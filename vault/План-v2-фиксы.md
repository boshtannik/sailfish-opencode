## Как воспроизводить/диагностировать (проверено)

**Запуск с полным логом (даёт пароль сервера и все события):**
```
export XDG_RUNTIME_DIR=/run/user/100000 WAYLAND_DISPLAY=../../display/wayland-0 \
  QT_QPA_PLATFORM=wayland EGL_PLATFORM=wayland \
  DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/100000/dbus/user_bus_socket RUST_LOG=debug
killall harbour-opencode; killall opencode; sleep 1
rm -f ~/.cache/harbour-opencode/app.log
setsid invoker --type=silica-qt5 -s /usr/bin/harbour-opencode >/dev/null 2>&1 &
```
Через ~14 c в `~/.cache/harbour-opencode/app.log` будет:
`[opencode] server listening on http://127.0.0.1:PORT` и `[opencode] server password <PW>`.

**Снять полную последовательность событий хода (ground truth):**
```
(curl -sN -u opencode:$PW http://127.0.0.1:PORT/api/event & CP=$!
 sleep 2
 curl -s -u opencode:$PW -X POST http://127.0.0.1:PORT/api/session/$SID/prompt \
   -H 'content-type: application/json' -d '{"text":"ответь словом ок"}' -o /dev/null
 sleep 20; kill $CP) > /tmp/sse.txt
grep -aoE '"type":"[a-z._-]+"' /tmp/sse.txt | sort | uniq -c
```
`SID` — активная сессия (лог `активная сессия: ses_...` или `GET /api/session`).

**Abort:** то же + `curl -X POST .../api/session/$SID/interrupt` вместо ожидания.

## СНЯТО ЖИВЬЁМ (это и есть корень багов 2 и 2b)

**Нормальный ход 2.0.32 (полная последовательность):**
```
session.inbox.enqueued
session.inbox.delivered
session.execution.started
session.step.started
session.reasoning.started / delta / ended
session.text.started / delta / ended
session.step.streamed

```
**НЕТ `session.idle`! НЕТ `session.status`! НЕТ `turn.idle` в конце хода.**

**Abort 2.0.32:**
```
...
session.step.failed   data.error = {type:"aborted", message:"Step interrupted"}
session.execution.interrupted   data = {sessionID, reason:"user"}
```

Payload'ы:
- `session.execution.started/succeeded/failed`: `{sessionID}`
- `session.execution.interrupted`: `{sessionID, reason}`
- `session.step.failed`: `{sessionID, assistantMessageID, error:{type,...}}`

## БАГ 2 — плашка зависает жёлтой ("работает"), не возвращается в покой

**Корень:** наш код ждёт завершения по устаревшему `session.idle` (`main.rs::on_v2_idle`, гейт
`env.kind == "session.idle"`), который в этом потоке **не приходит**. Реальный конец —
`session.execution.succeeded`. Он у нас **распознан, но игнорируется**
(`dispatcher.rs` ветка `EXECUTION_*` возвращала просто `true`). Отсюда вечный `busy`.

**Фикс (уже частично внесён, см. ниже «Состояние рабочего дерева»).**
- `on_v2_idle` должен флашить ответ на `session.execution.succeeded` и `session.execution.interrupted`.
- Обработку конца хода держать зеркально v1-пути (`main.rs` v1 idle-блок ~стр. 966).

## БАГ 2b — abort (кнопка «квадратик») красит плашку в красный

**Корень:** на abort сервер шлёт `session.step.failed` с `error.type == "aborted"`, а наш
`STEP_FAILED`-арм → `on_session_error_v2` → `status="error"` (красный). Плюс
`session.execution.interrupted` игнорировался и не сбрасывал в idle. В v1 step-событий нет — потому
там abort был чистым.

**Фикс (решение Jack: как в v1 — зелёный idle):**
- `STEP_FAILED`: не поднимать error, если `error.type == "aborted"` (хелпер `is_aborted_error`).
- `session.execution.interrupted` → конец хода (idle), НЕ error.
- `session.execution.failed` (реальный сбой) → error.

## БАГ 1 — переключение версии API v1/v2 в настройках не работает корректно

**Решение Jack: ГОРЯЧЕЕ применение** (без перезапуска приложения).

**Три дефекта (разведка ниже надёжна, файлы/строки):**
1. **QML никогда не читает настройки при старте.** `bridge.get_settings()`/`save_settings()` определены
   (`bridge/app.rs:346-361`), но **не вызываются из QML**. `settings_shared` на холодном старте = `""`
   (`bridge/app.rs:84`), поэтому `bridge.settings_json()` = `""`, guard `if (sj !== "")` не проходит
   (`harbour-opencode.qml:908-920`), и `app.apiVersion` остаётся QML-дефолтом `"v2"` — **визуально
   «настройка не переживает рестарт»**, хотя Rust-воркер читает файл сам (`main.rs:170`).
   → **Фикс:** вызвать `bridge.get_settings()` из QML при старте (до первого `poll()`), затем
   распарсить в `app.apiVersion`/`app.workdir`.
2. **Смена в рантайме только пишет файл.** `Cmd::SetApiVersion` (`main.rs:1505-1512`) = load→set→save→
   обновить `settings_shared`. Воркер **не перечитывает** настройку; адаптер выбирается один раз на
   старте (`main.rs:169-177`, `run_stream_adapter` `main.rs:325-372`). → «настройка ни на что не влияет».
   → **Фикс:** при `SetApiVersion` будить воркер — пересоздать адаптер + переподключить SSE с новой
   версией (сигнал в воркер-таск).
3. **SSE-реконнект переиспользует замороженное значение** (`main.rs:285-322` — `run_stream_adapter`
   в цикле с одним `api_version`). → перечитывать настройку при реконнекте, либо hot-switch из п.2.

Связанное (проверить при фиксе): `mailbox`-дефолт `default_api_version() == "v2"` (`settings.rs:36-38`);
QML-константа дефолта `property string apiVersion: "v2"` (`harbour-opencode.qml:287-291`);
ComboBox `GlobalSettingsPage.qml:310-335` (флаг `armed` — от программной записи).
