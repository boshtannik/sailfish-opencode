# План миграции клиента на opencode v2

**Статус:** 🟡 план составлен (2026-10-19), работа не начата. Ветка репозитория — **`v2`**.
**Цель:** перевести Sailfish-клиент (`harbour-opencode`) с протокола opencode **v1** на **v2**, оставаясь up to date с upstream (клиент для сообщества).
**Связанные заметки:** [[План]], [[Структура]], session-memory (personal_secretary) — раздел «2026-10-19 — возможный путь — форк под opencode v2».

---

## 1. Зачем и что меняется в v2

opencode v2 заявляет **три осознанных breaking change**, из которых нас касаются **две**:

1. **Плагины** — новый plugin API (нас не касается, плагинов у нас нет).
2. **Server API и клиенты — новый контракт** ← **наша основная работа**.
3. Конфиг TUI-клиента `tui.json(c)` → один `cli.json` (нас не касается, у нас свой QML-клиент).

Вне этих зон v1-функционал заявлен совместимым. **v2-бинарь ставится вместо v1** (не side-by-side); миграция данных v1→v2 (`kv.migration.v1-v2`) — **одноразовая** (известная проблема: сессии v1, созданные уже после первого запуска v2, в v2 не импортируются — issue #49641). Это надо учитывать при тестировании форка: **не смешивать v1 и v2 в одном каталоге данных**.

### Источники информации
- Доки: `https://opencode.ai/v2/docs` (интро/CLI), `https://opencode.ai/v2/docs/api/` (API-референс, 143 операции), `https://opencode.ai/v2/docs/migrate-v1/` (миграция). `/v2/docs/server` и `/v2/docs/sdk` → **404**.
- **Важно:** **состав SSE-событий в доке НЕ документирован** (см. раздел 4) — это неожиданно и означает, что события надо добывать из кода/эмпирики, а не из доки.

## 2. HTTP API: v1 → v2 (полная карта наших вызовов)

Все наши вызовы (24) в `opencode-client/src/api/*.rs`. Префикс v2 — **`/api/*`**.

| Наша функция (v1) | v1 путь / тело | v2 путь / тело | Комментарий |
|---|---|---|---|
| `create_session` | `POST /session` (—) | `POST /api/session` (`{id?, parentID?, title?, agent?, model?, location?, metadata?, permissions?}`) → `{data: Session.Info}` | появились `agent`/`model`/`location` при создании |
| `list_sessions` | `GET /session` | `GET /api/session` (курсор `cursor.next/previous`, `limit/order/search/parentID/directory/...`) | курсорная пагинация вместо массива |
| `rename_session` | `PATCH /session/{id}` `{title}` | `PATCH /api/session/{id}` (`{title?, metadata?, permissions?}`) → 204 | ответ 204, не объект |
| `delete_session` | `DELETE /session/{id}` | `DELETE /api/session/{id}` → 204 | + удаляет детей |
| `get_session` | `GET /session/{id}` | `GET /api/session/{id}` → `{data: Session.Info}` | обёртка `data` |
| `fork_session` | `POST /session/{id}/fork` `{messageID?}` | `POST /api/session/{id}/fork` `{before?}` | **переименовано поле** |
| `revert_session` | `POST /session/{id}/revert` `{messageID}` | `POST /api/session/{id}/revert/stage` `{messageID, files?}` → `{data: Session.Revert}` | revert разбит на 3 роута |
| `unrevert_session` | `POST /session/{id}/unrevert` | `POST /api/session/{id}/revert/commit` (—) → 204 | + `DELETE /api/session/{id}/revert` (clear) |
| `share_session` | `POST /session/{id}/share` | **нет в v2 API-референсе** | фичу share нужно перепроверить/выяснить судьбу |
| `unshare_session` | `DELETE /session/{id}/share` | **нет в v2 API-референсе** | то же |
| `summarize_session` | `POST /session/{id}/summarize` `{providerID, modelID}` | `POST /api/session/{id}/compact` (`{id?, ...}`, delivery/steers) | компакция → отдельный тип сообщения (см. §3) |
| `providers` | `GET /config/providers` | `GET /api/provider` + `GET /api/model` (+ `GET /api/model/default`) | каталог моделей разделён |
| `session_todo` | `GET /session/{id}/todo` | **нет в v2 API-референсе** (есть `session.todo` в спекуляции dev) | перепроверить |
| `session_messages` | `GET /session/{id}/message` → `[{info, parts}]` | `GET /api/session/{id}/message` → `{data: Session.Message.Info[], cursor{previous,next}}` | **ответ в конверте + курсор; сообщения без `parts`** |
| `set_model` | `POST /api/session/{id}/model` `{model:{id,providerID}}` | `POST /api/session/{id}/model` `{model: Model.Ref}` → 204 | почти совпало; тело `Model.Ref` |
| `set_session_agent` | `POST /api/session/{id}/agent` `{agent}` | `POST /api/session/{id}/agent` `{agent}` → 204 | совпало |
| `prompt_async` | `POST /session/{id}/prompt_async` `{messageID?, model?, agent?, parts:[{type:"text",text}]}` | `POST /api/session/{id}/prompt` `{id?, text*, files, agents, skills, metadata, delivery, resume}` | **`parts[]` → `text`; новые поля delivery/resume** |
| `abort` | `POST /session/{id}/abort` | `POST /api/session/{id}/interrupt` (по API-референсу `session.interrupt`) | перепроверить имя (в dev-спеке был abort) |
| `answer_permission` | `POST /session/{id}/permissions/{pid}` `{response:"once"\|"always"\|"reject"}` | `POST /api/session/{id}/permission/{reqID}/reply` `{decision:"once"\|"always"\|"reject", message?}` | путь + поле |
| `answer_question` | `POST /question/{id}/reply` `{answers:[[labels]]}` | формы: `session.form.*` | другая модель (см. §5) |
| `reject_question` | `POST /question/{id}/reject` | формы: `session.form.cancel`/`reply` | то же |
| `set_api_key` | `PUT /auth/{providerID}` `{type,key}` | credentials/integrations (`credential.*`, `integration.*`) | другая модель |
| `health` | `GET /global/health` | `GET /api/info` | серверная инфо-ручка |
| `global_dispose` | `POST /global/dispose` | прямой замены нет: `POST /api/location/reload` | после login — перезагрузка локации |

### Известные «неудобные» места
- `POST /api/session/{id}/model` и `/agent` — совпали, но в v1-доке они значились как `/api/...` (не `/api` группы v1), так что это уже было полу-v2.
- **share/unshare/todo/auth/questions** — в v2 API-референсе прямых аналогов не видно. Нужно: (а) выяснить по коду v2, что заменяет; (б) решить судьбу фич (выкинуть/переделать).
- Обёртка ответов: v2 любит `{data: ...}` и `204 No Content` — вместо «голых» объектов v1.

## 3. Модели данных: v1 → v2 (самое трудоёмкое)

### Сообщения
- **v1 (у нас):** `Message` — enum по `role`: `User {…}`, `Assistant {…, mode, parentID, modelID, providerID, cost, tokens, finish}`. `mode:"compaction"` = сжатие истории (наш недавний фикс live-компакции крутится вокруг этого).
- **v2:** **нет `role`**; `Session.Message.Info` — union по **`type`**:
  `user | assistant | system | synthetic | skill | shell | compaction | idle | agent-switched | model-switched | location-switched`.
  - `type` — точный тег: `"user"`, `"assistant"`, `"compaction"` (со `status: running|completed|failed`, `reason: auto|manual`), `"idle"` (`outcome: succeeded|failed|interrupted`) и т.д.
  - `Session.Message.Assistant` содержит `content: [Text | Reasoning | Tool]` — **парты теперь внутри сообщения**.
- **Следствие:** наш недавний фикс live-компакции переосмысляется: в v2 компакция — **отдельный тип сообщения** с собственным статусом, а не assistant-`mode`.

### Парты
- **v1:** отдельный `Part` enum (`Text | Reasoning | Tool | File | Compaction`), отдельные события `message.part.updated` / `message.part.delta`.
- **v2:** **сущности `Part` больше нет** — текст/reasoning/tool = элементы `content[]` в assistant-сообщении. Нужно переписать всю логику ленты (инлайн-тулы, живой стрим текста, reasoning).

### Сессия
- **v2 `Session.Info`:** `id, parentID, fork{sessionID, boundary}, projectID, agent, model, cost, tokens, outcome, time{created, updated, idle, viewed, archived}, title, subpath, metadata, permissions, revert{messageID, partID, snapshot, files}, location`.
- Наш `Session {id, projectID, directory, parentID, summary, share, title, version, time}` → пересобрать.

### Permission / Question
- **v2 permission id:** `^per` (было, вероятно, иное); reply: `{decision, message?}`.
- **Questions → Forms:** модель форм (`session.form.*`, `form.list`). Наша question-модель (`{id, sessionID, questions, tool}`) не соответствует.

### Ключи/константы
- `types/keys.rs` (наш единый источник JSON-ключей) — перепривязать под новые имена и дискриминаторы (`type` вместо `role`, `mode` и т.д.).

## 4. События (SSE): **недокументированы в доке** ⚠️

### Факт
- v2 эндпоинт: **`GET /api/event`** (было `/global/event`), `text/event-stream`.
- Envelope: `{id, event, data}`, где **`data` объявлен как непрозрачная строка** (`V2EventEncoded`), **без структуры `{type, properties}`** и **без перечисления имён событий** в доке.
- Есть дурабельные альтернативы: `GET /api/experimental/session/{id}/log` (конечный реплей с курсором `after`) и `GET /api/session/{id}/history` (конечные 50 публичных durable-событий).

### Почему это не блокер, но требует работы
- **Док не описывает события → источник правды = код v2-клиента** (см. решение ниже) и/или эмпирика (сырой SSE).
- У нас в `types/event.rs` уже объявлена большая часть будущего протокола: `permission.v2.*`, `question.v2.*`, **вся семья `session.next.*`** (tool/shell/text/reasoning/step/compaction/revert/agent.switched/model.switched/...). Вероятно, подсмотрено из `@opencode-ai/sdk@1.18.31`. Это может **сильно упростить** миграцию: каркас событий уже намечен.
- **Наш живой стрим сейчас идёт по старым `message.part.updated` / `message.part.delta`.** Если v2 уводит стрим в `session.next.text.*` / `session.next.reasoning.*` / `session.next.step.*` / `session.next.compaction.*` — **эту часть надо перевести** (иначе живой вывод сломается).

### Текущее состояние диспетчера
- `Event` enum — **91 вариант** (90 прямых + агрегат `sync` с 35 вложенными). Диспетчер **исчерпывающий, без catch-all** (правило проекта): **обрабатывает 29**, **62 → `note_unimplemented` (warn)**.
- Обработаны (наши «несущие»): `session.status/idle/created/updated/deleted/compacted/error`, `permission.*` (v1+v2), `message.updated/part.updated/part.delta`, `question.*` (v1+v2), `session.next.tool.*` + `session.next.shell.*`.

### Решение по добыче спецификации (согласовано с Jack)
1. **Скачать официальный v2-клиент и читать его код** — выдирать принципы работы событий, envelope, имена событий, формы запросов. Это основной путь.
2. При необходимости — **эмпирика**: запустить v2-бинарь и снять сырой SSE + `curl` по эндпоинтам (запасной путь).

## 5. Что переиспользуется как есть

- **Весь голосовой стек** (STT whisper.cpp, PTT, TTS piper, каталог/скачивание моделей) — **не зависит** от opencode API (кроме путей промпта/озвучки ответа).
- **QML-UI целиком** (страницы Chat/Sessions/GlobalSettings/SessionSettings, обложка, уведомления, звуки) — меняется только слой данных под ним.
- **Серверная обвязка** (`ServerGuard`, reap сирот, health-poll) — правки минимальны.
- **Настройки/уведомления/обложка** — как есть.

## 6. Архитектурное решение: адаптер протоколов (v1/v2)

**Идея (рекомендация):** не «бампать» версию в лоб, а **вынести серверный протокол за трейт-адаптер**:

```
UI / state / event hub
        │
        ▼
  trait OpenCodeApi        ← общий интерфейс (create_session, prompt, history, events…)
     ├── V1Adapter         ← текущая реализация (opencode 1.19.0)
     └── V2Adapter         ← новая (opencode 2.x)
```

**Плюсы:**
- Миграция = добавление `V2Adapter`, а не переписывание клиента; v1-адаптер живёт рядом (регресс-контроль, постепенный переход).
- Форк может поддерживать обе версии, пока v2 не станет единственной.
- Тестируемо: адаптеры можно мокать.

**Минусы:** разовая работа по выносу интерфейса. Но она окупается: сейчас `main.rs`/`dispatcher.rs`/`api/*` плотно смешаны.

**Развилка, требующая решения Jack:** делать адаптер сразу (дороже старт, дешевле финиш) или сначала грубо переписать `api/`+`types/` под v2 в ветке и лишь потом рефакторить. Рекомендация — **адаптер сразу**, т.к. иначе v2-правки размажутся по всему коду.

## 8. Порядок работ (этапы)

1. **Разведка кода v2-клиента** → зафиксировать: реальные имена SSE-событий и их payload, точные тела `prompt`/`compact`/`fork`/`revert`/`permission`, судьба share/todo/auth/questions, форма `Session.Message.Info`.
2. **Вынос трейта `OpenCodeApi`** из текущего кода (v1 за адаптером), без смены поведения — «зелёный» регресс (собрать, задеплоить, убедиться, что чат жив).
3. **Скелет `V2Adapter`** (базовые: session CRUD, prompt, history, event-стрим), переключение по флагу.
4. **Типы v2** (message/content/compaction/session/permission) — тут сломается больше всего.
5. **События v2** — живой стрим, тулы, reasoning, компакция.
6. **Фичи-сироты**: share, todo, questions(forms), auth — выяснить и решить.
7. **Тесты** (`make test` — протокол на хосте, `make test-sdk` — lib в SDK) + сборка RPM + ручной тест на телефоне.
8. **Чистка**: удалить v1-адаптер (если решено перейти окончательно), обновить доки.

## 9. Риски

- **Состав событий не документирован** → без разведки кода v2 легко «угадать» неверно. Митигация: этап 1 обязателен.
- **Одноразовая миграция данных** v1→v2 — легко испортить рабочую v1-сессию при тестах. Митигация: тестовый каталог данных.
- **Компакция** переосмысляется (отдельный тип сообщения) — недавний фикс живого бабла придётся переделать.
- **Фичи без аналога** (share/todo) — возможна потеря функционала; решать по коду v2.
- **Адаптер vs быстрая переписка** — развилка объёма; рекомендация — адаптер.
