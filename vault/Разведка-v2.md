### 1.2. `assistant.content[]` — union по **`type`** (v1: отдельные `Part`)

`"streaming"` (`input: string` — сырой частичный JSON) | `"running"` (`input`, `metadata`) |

`Content` (результат тула, `packages/schema/src/tool.ts:67`): `{type:"text", text}` |

## 3. Envelope и живой стрим (ключевое для SSE)

**Эндпоинт:** `GET /api/event` (было `/global/event`). Фрейм **без `event:`/`id:` линий**:

```
data: {"id":"evt_…","type":"session.text.delta","created":123,"data":{…}}

: heartbeat
```

- Первый кадр всегда `{id, type:"server.connected", data:{}}`.
- Heartbeat — комментарий `: heartbeat` раз в 15 c.
- Envelope (`packages/schema/src/event.ts:67`): `{id, type, created, data, location?, metadata?, durable?}`.
  **`data` — вложенный объект**, не JSON-строка (в доке было `V2EventEncoded` — это про branded-типы).
- Диспетчеризация — по `event.type`, не по имени SSE.
- **Volatile-контракт:** медленный потребитель → overflow (лимит 4096) и обрыв; пропущенные при разрыве
  события **не восполняются**. Durable-реплей — отдельным эндпоинтом.

**Реплей durable (для истории/догона):** `GET /api/experimental/session/{id}/log?after=<seq>&follow=`
(курсор — эксклюзивный `seq`, шлёт durable-события сессии + маркер `{type:"log.synced"}`).
Есть и `GET /api/session/{id}/history` (durable 50).

## 4. Алгоритмы обработки событий (как переписываем диспетчер)

**Текущий живой стрим (v1)** идёт по `message.part.updated` / `message.part.delta`;
**в v2 это `session.text.*` / `session.reasoning.*` / `session.tool.*`** — перевести обязательно,
иначе лента встанет.

Новая модель (маппинг на наш текущий код):

1. **Текст ответа.** `session.text.started{ordinal}` → создать/пометить bubble №`ordinal`;
   `session.text.delta{ordinal, delta}` → **append к bubble** (это наш live-stream);
   `session.text.ended{ordinal, text}` → финальное значение (сверка/замена).
   Идентификация части — `(assistantMessageID, ordinal)` (в v1 у части был `partID` — теперь ordinal).
2. **Reasoning.** Аналогично `session.reasoning.*` → наш `[[think]]`-bubble.
3. **Тул-колл.** `session.tool.input.started` (имя+id) → `…input.delta` (стрим аргументов) →
   `…input.ended` (готовый JSON-текст) → `session.tool.called` (клик по тулу) →
   `…progress` (статус) → `session.tool.success`/`failed` (результат, `content[]`).
   Наш текущий инлайн-тул-виджет переписать под эту последовательность.
4. **Шаги.** `session.step.started`/`streamed`/`ended`/`failed` — границы одного прогона модели;
   `step.ended` несёт `finish`/`cost`/`tokens`. Использовать для статуса «busy/ready».
5. **Компакция.** Была `assistant.mode:"compaction"` → теперь:
   `session.compaction.started{reason}` → `…delta{text}` (растёт бабл) → `…ended{text}` /
   `…failed`. Наш недавний фикс live-компакции **переосмыслить под этот поток**.
6. **Статус сессии.** `session.status{status:{type: idle|busy|retry}}` — новый FSM;
   `session.idle` — deprecated, оставить как fallback.
7. **Permission.** `permission.asked` → показать запрос (`resources[]`, `action`);
   ответ `permission.replied`. Ответ шлём новым телом `{decision, message?}`.
8. **Form (бывшие questions).** `form.created{form}` → рендер полей по `field.type`;
   ответ `{answer:{...}}`; `form.replied`/`form.cancelled` — закрыть панель.
9. **Сессии CRUD.** `session.created/renamed/deleted` — обновить список; `session.created`
   больше не отдаёт `share`/`version` в прежнем виде (пересобрать модель).

**Дисциплина match:** добавляем ВСЕ новые теги в `Event` enum; каждому — либо обработка,
либо `note_unimplemented`. Никаких `_ =>`; неизвестные типы — отдельный вариант `Unknown`
(serde `#[serde(other)]`) с `note_unimplemented`, чтобы новые события из upstream не падали,
но и не прятались молча.

## 6. Что это значит для этапа 2 (вынос трейта)

Трейт `OpenCodeApi` должен абстрагировать **две смены модели**:
1. Тексты/дельты: v1 `message.part.*` ↔ v2 `session.text/reasoning/tool.*`.
2. Сообщения: v1 `role`+`parts` ↔ v2 `type`+`content[]` (для истории).

Рекомендуемые методы трейта: `create/list/get/rename/delete/fork_session`,
`prompt`, `interrupt`, `compact`, `revert_stage/clear/commit`, `permission_reply`,
`form_reply`, `providers/models`, `info`, `messages_history`, `subscribe_events`.
v1-адаптер = текущий код как есть; v2-адаптер — новый.

### 7.1. РЕШЕНО: user-messageID под v2 (2026-10-20) ✅

**Вопрос:** в v2 user-`messageID` не приходит в SSE (v2 стримит только assistant-side). Как
прикрепить id к свежему user-пузырю (revert/fork)?

**Ответ (проверено по исходникам `packages/core/src/session/` @ `8f7b012`):**
- `POST /api/session/:id/prompt` → `success: { data: SessionInbox.User }` (`protocol/src/groups/session.ts:326`).
- `SessionInbox.User.id` имеет тип `SessionMessage.ID` (`schema/src/session-inbox.ts:53,59`) — **тот же
  id, что у сообщения**.
- `Session.prompt` создаёт `messageID = input.id ?? SessionMessage.ID.create()` и admits inbox-элемент
  под этим id (`core/src/session/session.ts:149,166`).
- Проектор `SessionEvent.InboxDelivered` вставляет user-сообщение с `id: input.id`
  (`core/src/session/projector.ts:618–647`), где `input.id = event.data.inboxID`.

**Итог:** `data.id` из ответа `POST /prompt` = `MessageInfo.id` user-сообщения. Берём его прямо из
HTTP-ответа, без ожидания SSE. Реализовано: трейт `prompt_async` → `Result<Option<String>, String>`
(v1 `None` — id приходит через `message.updated`; v2 `Some(id)` — из ответа).

## 8. Наблюдение с живого бинаря (этап 3, `api_version:v2`)

При переключении клиента на `V2Adapter` (флаг `settings.api_version`) **бандленный `opencode`
(1.19.0) уже отдаёт v2-подобные события** по текущему SSE-потоку — в логе воркера появились
теги, которых нет в v1: `plugin.added`, `catalog.updated`, `reference.updated`,
`integration.updated` (плюс обычный `server.connected`). Наши `event.rs`/`dispatcher.rs` их
пока не знают → `note_unimplemented` (как и задумано).

**Что это значит:**
- Бандленный сервер **умеет v2** (или часть событий уже v2-стиля) — на этапе 5 (события v2)
  проверить это эмпирически: какие теги реально приходят, и в каком envelope (`data` — объект?).
- Наши «несущие» v1-события (`message.part.updated/delta`) при этом ещё работают, так что
  переключение флага **не ломается** на старте (SSE подключается), но v2-путь неполон до этапа 5.
- `session_todo` под v2 ожидаемо падает с нашим явным `Err("todo is not available …")` —

### 8.1. Бандленный opencode 1.19.0 vs исходники `8f7b012` — РАСХОЖДЕНИЯ (2026-10-20)

Проверено эмпирически против живого сервера телефона (`127.0.0.1:4096`, `--version` = **1.19.0**).
**Бандленный 1.19.0 старее dev-исходников `8f7b012`** — часть схем из §5 не совпадает:

- **prompt (БЫЛ 400).** 1.19.0 НЕ принимает плоское `{text,...}`: отвечает
  `InvalidRequestError "Missing key at [\"prompt\"]"` (400). Правильное тело —
  **`{prompt: {text, agents?}}`** (вложено под `prompt`). Ответ — `{data: {id: "msg_…", …}}`,
  `data.id` = user-message ID. `agents` — массив объектов `Prompt.AgentAttachment` `[{name}]`,
  НЕ строк (`["build"]` → 400). **Исправлено в `api/v2.rs` (коммит `0a511fe`).**
- **update/rename НЕ доступен.** `PATCH /api/session/{id}` (и варианты `/rename`, `/title`,
  POST/PUT) в 1.19.0 отдают SPA-HTML (не совпало с роутом) — переименование сессии под v2
  в бандленном сервере отсутствует. (Аналог «сирот» share/todo.)
- Совпало (проверено 200/204): `create/list/get/delete` (envelope `{data}`), `fork`,
  `agent {agent}`→204, `model {model:{providerID,id}}`→204, `revert/stage {messageID}`→404
  (тело ок, только message не найден), `revert/commit`→204, `interrupt`→204,
  `providers {location,data}`. **compact** → `503 "Session compact is not available yet"` (серверная
  заглушка, не наша ошибка).

### 10.5. РАНТАЙМ-ОТЛИЧИЯ 2.0.32 (выяснено живой установкой на телефон, 2026-10-20) ⚠️
